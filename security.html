CC Defender · Enterprise only

Security in front of every request.

CC Defender is a hardened layer around CoolCloud. It runs before routing, before sessions, before apps and before the CLI can do anything. If an address is not welcome, it never reaches your data.

Ask about Enterprise See how it works

Brute-force lockout

Failed sign-ins are counted in SQLite, not memory. After the threshold the address is locked for a configurable window — a server restart does not give an attacker a fresh start.

Allow and deny lists

Exact addresses and CIDR ranges. An allow list turns CoolCloud into a private network service; a deny list shuts out known-bad addresses immediately. Allowed matches win over denies.

Country rules

Block whole countries by two-letter code. Address intelligence is cached for 24 hours, so the check is fast and works even when the lookup service is unavailable.

CLI and API guard

The same policy covers the REST API and the remote CLI. A blocked address gets a clear refusal with the block-page URL instead of a session, and admin commands cannot bypass it.

Encryption at rest

AES-256-GCM seals mail passwords, authenticator secrets and app storage. The key stays on the server, or outside the instance through CC_MASTER_KEY. The CLI token gets its own sealed store.

Visible decisions

Every block, unblock and denial is written to the Defender log and the audit trail. Admins can look up an address, see its network, and unblock it without touching the database.

Request lifecycle

Four checks before anything loads.

The guard is deliberately boring: one function, one decision, one place to audit.

1

Resolve the real address

Forwarded headers are trusted only from a local reverse proxy, so a client cannot spoof its way past the policy.

2

Match the policy

Allow list, localhost exemption, active lockout, deny list and cached country — in that order. When an allow list exists, everything not on it is refused.

3

Refuse before routing

A browser is sent to a branded block page with the reason and retry time. An API or CLI call gets a JSON 403 with code: "defender". No app code runs.

4

Keep watching

Every tab open, focus and visibility change asks the server to re-check and enrich the address. A policy change takes effect on the next request, even in an open tab.

When an address is refused

A block page, not a stack trace.

Visitors see what happened, their address, when to retry and a support link. No internal paths, no version numbers, no hint about which accounts exist. The page is served by the server itself with a strict content-security policy and no external assets.

Configurable without a redeploy

Thresholds, windows, lockout length, lists, countries and the localhost exemption are saved to config.json and applied live. The console refuses to save rules that would lock out the administrator making the change.

Scope

What CC Defender protects.

Everything the server exposes — not only the sign-in screen.

Web interface

Page loads, static assets, the App Store, public forms and published websites all pass the guard.

REST API

Blocked callers receive a JSON refusal before authentication, so no token is evaluated and no data is read.

CLI

Remote CLI sessions inherit the same policy. The CLI stores its token encrypted and reports the block URL.

Public links

Share links, published sites and form pages are server routes, so they cannot be used to bypass a deny rule.

Data at rest

Secrets and app storage are sealed with authenticated encryption; tampering returns empty, never forged data.

Audit

Defender events sit beside the normal audit trail, ready for CSV/JSON export into your SIEM.
